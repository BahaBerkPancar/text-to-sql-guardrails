# M2: Safe executor + demo database

GOAL: Replace the template `items` code with the demo shop database, and run validated SQL through
guardrail layers 2 and 3 (plans/ROADMAP.md): a read-only Postgres role whose SELECT grants are
generated from `config/policy.toml`, and a read-only transaction with a statement timeout and a row
cap. Expose it as `POST /query`. Each layer must be proven by tests **on its own**, bypassing the others.

SCOPE: `src/text_to_sql_guardrails/` (except `guard/validator.py` — only bug fixes there, listed in
NOTES), `migrations/`, `tests/`, `scripts/smoke.sh`, `compose.yaml`, `Dockerfile`, `.env.example`,
`.github/workflows/test.yml`, `pyproject.toml`, `uv.lock`, `README.md` (setup section only),
`DECISIONS.md`, `CHANGELOG.md`.

DO NOT TOUCH: `plans/`, `config/policy.toml` (read it, don't change the allowlist), `AGENTS.md`,
`CLAUDE.md`. Never read `.env`. Do not touch any Docker container other than `t2s-test-pg`
(the `pulse-*` containers belong to another project).

TEST DATABASE: a Postgres 16 container is already running for you:
`TEST_DATABASE_URL=postgresql+psycopg://app:app@127.0.0.1:55432/app` (superuser `app`). Tests may
create/drop whatever they need inside it. Integration tests are marked `@pytest.mark.pg` and are
**skipped when `TEST_DATABASE_URL` is unset**, so plain `uv run pytest` still works without Docker.

STEPS:
1. **Remove the template**: `Item` model, `/items` endpoints and their tests, migration `0001_create_items`.
2. **Schema** (SQLAlchemy models + new Alembic migration `0001_shop_schema`):
   `customers(id, name, email, phone, city, country, created_at)`,
   `products(id, name, category, price numeric(10,2))`,
   `orders(id, customer_id→customers, status, ordered_at, total numeric(12,2))`,
   `order_items(id, order_id→orders, product_id→products, quantity, unit_price numeric(10,2))`,
   `staff_salaries(id, staff_name, role, salary numeric(12,2))`. Keep `test_migrations.py` green.
3. **Seed** `text_to_sql_guardrails/seed.py`: deterministic (`random.Random(42)`, fixed base date, no
   network, no Faker): ~200 customers across ~8 countries, ~40 products in ~6 categories, ~1000 orders
   over 2 years with consistent totals, ~10 salary rows. Idempotent (truncate-and-reload).
4. **Read-only role** `guard/roles.py`: `grant_statements(policy, role) -> list[str]` that builds
   `REVOKE ALL` on every table in `public` + `GRANT USAGE ON SCHEMA public` + **column-level**
   `GRANT SELECT (cols...) ON table` only for policy tables/columns; also
   `ALTER ROLE ... SET default_transaction_read_only = on` and `SET statement_timeout`. Quote
   identifiers safely. `apply_role(admin_engine, policy, role, password)` creates the LOGIN role if
   missing and runs the statements. Unit-test the generated SQL without a DB.
5. **Setup command** `t2s-setup` (console script): alembic upgrade head → seed (only if empty, or
   `--reseed`) → apply role. Uses `DATABASE_URL` (admin). Dockerfile CMD runs it, then uvicorn.
6. **Settings** (`config.py`): `database_url` (admin), `readonly_database_url`, `readonly_role`
   (`t2s_readonly`), `readonly_password`, `statement_timeout_ms` (3000), `policy_path`
   (`config/policy.toml`). Update `.env.example` with placeholders only.
7. **Executor** `guard/executor.py`: `run_readonly(sql, engine, timeout_ms, max_rows) -> QueryResult`
   (`columns`, `rows` as JSON-safe values — Decimal→str or float, datetime→ISO, `row_count`,
   `truncated`, `elapsed_ms`). In one transaction: `SET TRANSACTION READ ONLY`,
   `SET LOCAL statement_timeout`, execute, `fetchmany(max_rows + 1)` to detect truncation, always roll
   back. Map errors to typed exceptions: `QueryTimeout`, `QueryPermissionDenied`, `QueryFailed`
   (message without connection details).
8. **API**: `GET /health`; `GET /schema` → allowed tables/columns from the policy; `POST /query`
   `{"sql": "..."}` → validate (M1) → run on the read-only engine → `200 {"ok": true, "sql": <rewritten>,
   "columns", "rows", "row_count", "truncated", "elapsed_ms"}`; blocked → `200 {"ok": false,
   "stage": "validator", "violations": [{code, message}]}`; DB-level block/timeout → `200 {"ok": false,
   "stage": "database", "error": {code, message}}` with codes `TIMEOUT`, `PERMISSION_DENIED`,
   `QUERY_FAILED`. Request body max 10 000 chars (422 above). Engine/policy via FastAPI dependencies
   so tests can override them.
9. **Tests**:
   - unit (no DB): `grant_statements` output; `/health`, `/schema`; `/query` with a blocked query
     returns the validator violations without touching a DB (override the engine dependency with one
     that fails if used).
   - `pg` integration, using the role and seed set up in a session fixture:
     - layer 2 alone (raw SQL on the read-only engine, validator skipped): `SELECT email FROM customers`,
       `SELECT * FROM staff_salaries`, `SELECT c FROM customers c` → permission denied;
       `DELETE FROM orders`, `CREATE TABLE x(i int)` → fail; data unchanged afterwards.
     - layer 3 alone: `SELECT pg_sleep(5)` with `timeout_ms=300` → `QueryTimeout` in < 2 s; a big query
       with `max_rows=10` → 10 rows, `truncated=True`.
     - end-to-end `/query`: a normal aggregate returns correct numbers (compute the expected value with
       the admin engine); seed is deterministic (two seeds → same checksum).
10. **CI** (`.github/workflows/test.yml`): `services: postgres:16` with health check, set
    `TEST_DATABASE_URL`, run pytest (pg tests included), ruff, then smoke. **Smoke** (`scripts/smoke.sh`):
    default port 8010, check `/health` and one `POST /query` that returns `ok: true`.
11. Docs: DECISIONS (column-level grants generated from the policy; why the result is 200 with
    ok=false; why tests skip without Postgres; known gap: functions like `pg_sleep` are executable by
    PUBLIC, so layer 3's timeout covers them), CHANGELOG, README setup section.
