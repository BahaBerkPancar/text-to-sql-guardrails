# M1: Guardrail core (SQL validator)

GOAL: A pure-Python SQL validator that decides whether a query an LLM wrote may run, and returns a
safe rewritten query or machine-readable reasons why not. It is the first guardrail layer
(see plans/ROADMAP.md). No database and no LLM in this milestone.

SCOPE:
- `pyproject.toml` / `uv.lock` (add `sqlglot` via `uv add sqlglot`)
- new: `config/policy.toml`
- new: `src/text_to_sql_guardrails/guard/__init__.py`, `guard/policy.py`, `guard/validator.py`
- new: `tests/test_policy.py`, `tests/test_validator.py`
- `DECISIONS.md`, `CHANGELOG.md`

DO NOT TOUCH: `main.py`, `models.py`, `db.py`, `migrations/`, the existing tests, `compose.yaml`,
`Dockerfile`, `.github/`, `plans/`. Never read `.env`.

STEPS:
1. **Policy file** `config/policy.toml` for the demo shop schema:
   - `[limits] default_limit = 100`, `max_limit = 500`
   - allowed tables and their allowed columns:
     - `customers`: id, name, city, country, created_at   (NOT email, phone)
     - `products`: id, name, category, price
     - `orders`: id, customer_id, status, ordered_at, total
     - `order_items`: id, order_id, product_id, quantity, unit_price
     - (`staff_salaries` exists in the DB later but is NOT listed, so it is denied)
   - `[functions] allowed = [...]`: a short list of extra function names allowed beyond the built-in
     safe set (can be empty).
2. **`guard/policy.py`**: frozen dataclass `Policy` (tables → set of columns, default_limit,
   max_limit, extra allowed functions); `load_policy(path)` using stdlib `tomllib`; names
   compared case-insensitively. Validate the file (limits positive, default ≤ max, no empty table).
3. **`guard/validator.py`**: `validate(sql: str, policy: Policy) -> ValidationResult` where
   `ValidationResult` has `ok: bool`, `sql: str | None` (rewritten, Postgres dialect, only when ok)
   and `violations: list[Violation]`; `Violation(code: str, message: str)`. Codes are a `StrEnum`:
   `PARSE_ERROR, MULTI_STATEMENT, NOT_SELECT, FORBIDDEN_NODE, TABLE_NOT_ALLOWED,
   COLUMN_NOT_ALLOWED, FUNCTION_NOT_ALLOWED, BAD_LIMIT, EMPTY`.
   Rules (parse with sqlglot, dialect `postgres`):
   - Empty/whitespace → EMPTY. Parse failure → PARSE_ERROR. More than one statement → MULTI_STATEMENT.
   - Root must be a `Select` or a set operation (`Union/Intersect/Except`) of selects, optionally
     with a `WITH` clause. Anything else → NOT_SELECT.
   - Walk the **whole tree**: any Insert/Update/Delete/Merge/Create/Drop/Alter/TruncateTable/Command/
     Copy/Set/Transaction/Commit/Rollback/Grant, `SELECT ... INTO`, locking clauses (`FOR UPDATE/SHARE`)
     → FORBIDDEN_NODE. This catches data-modifying CTEs (`WITH x AS (DELETE ...) SELECT ...`).
   - Every real table (not a CTE name) must be in the policy; schema must be absent or `public`.
     `pg_catalog.*`, `information_schema.*`, `pg_*` tables etc. → TABLE_NOT_ALLOWED.
   - Columns: qualify the query with `sqlglot.optimizer.qualify` using a schema built **only from the
     allowed columns**, so unknown/denied columns fail → COLUMN_NOT_ALLOWED, and `*` / `t.*` expand to
     allowed columns only. Postgres whole-row references (`SELECT c FROM customers c`,
     `row_to_json(c)`) must be rejected (they would return denied columns).
   - Functions: allow sqlglot's known safe function classes (aggregates, string, math, date/time,
     CASE/COALESCE/CAST, window functions — decide the exact list and write it in DECISIONS.md) plus
     `policy.extra_functions`. Any unknown/anonymous function not allowlisted → FUNCTION_NOT_ALLOWED.
     Explicitly test that these are blocked: `pg_sleep`, `pg_read_file`, `pg_ls_dir`, `set_config`,
     `current_setting`, `dblink`, `lo_import`, `lo_export`, `version`, `query_to_xml`, `generate_series`.
   - LIMIT: no LIMIT → add `default_limit`; literal LIMIT > `max_limit` → clamp to `max_limit`;
     non-literal or negative LIMIT/OFFSET → BAD_LIMIT. For set operations, apply to the outer query.
   - Collect all violations (don't stop at the first) where practical; `ok` is true only with none.
   - The returned `sql` is the rewritten, qualified query (the one that would be executed).
4. **Tests** (`tests/test_validator.py`, parametrized, at least 40 cases total):
   - allowed: simple select, joins, group by/having, CTEs, subqueries, UNION, window functions,
     ORDER BY, LIMIT kept/clamped/added, `SELECT *` expanding to allowed columns only.
   - blocked: each FORBIDDEN_NODE kind, stacked queries `SELECT 1; DROP TABLE x`, comment tricks
     (`SELECT * FROM orders -- ; DROP ...`, `/* */`), data-modifying CTE, denied column directly / via
     alias / via subquery / via `*` on a join, whole-row reference, denied table, system catalogs,
     schema-qualified tricks (`public.staff_salaries`, `"STAFF_SALARIES"` quoting/case), each dangerous
     function above, `SELECT INTO`, `FOR UPDATE`, bad limits.
   - `tests/test_policy.py`: loads `config/policy.toml`; rejects an invalid policy.
5. Docs: DECISIONS.md entry (why sqlglot AST over regex; allowlist over denylist; the function list;
   whole-row reference risk). CHANGELOG "Unreleased" line.
