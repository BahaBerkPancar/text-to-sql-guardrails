# M5: Showcase (README, demo page, demo GIF)

GOAL: Make the repo understandable in 30 seconds for someone browsing MF's GitHub: a README that
leads with the problem and the guardrail layers, the M4a benchmark tables, a small web page to try
it, and a demo GIF recorded from that page. No live LLM numbers yet (no API key): the page must
work without credentials and say clearly when `/ask` is not configured.

SCOPE: `README.md`, new `src/text_to_sql_guardrails/web/` (static `index.html`, `app.js`,
`style.css`), `main.py` (serve the page at `/` and static files; no API changes), new
`scripts/record_demo.py` (or `.sh`), new `docs/` (diagram, `demo.gif`, screenshots), `tests/`,
`pyproject.toml`/`uv.lock` (dev-only deps if needed), `DECISIONS.md`, `CHANGELOG.md`.

DO NOT TOUCH: `plans/`, `config/`, `guard/`, `llm/`, `pipeline.py`, `bench/` data and results,
`migrations/`, `.github/workflows/test.yml` (unless a new test needs nothing extra — then leave it).
Never read `.env`. Never call the real Anthropic API. Don't make the repo public (MF decides).

STEPS:
1. **Demo page** at `GET /` — plain HTML/CSS/JS, no build step, no external CDN (works offline),
   light and dark via `prefers-color-scheme`, readable at phone width.
   - Two modes in tabs: **Ask** (question → `POST /ask`) and **Run SQL** (`POST /query`).
   - Result panel: the rewritten SQL that actually ran (monospace), a results table (cap display at
     the returned rows, show `truncated`), row count and elapsed ms; or a **blocked** card that names
     the stage (validator / database / model) and lists each violation code with its message.
   - On `/ask` returning 503 `LLM_NOT_CONFIGURED`: a calm notice that the model isn't configured, and
     a link that switches to Run SQL with an example query. Never show stack traces.
   - An "Try an attack" row of 6 one-click examples taken from `bench/attacks.yaml`
     (e.g. denied column, whole-row ORDER BY oracle, stacked DROP, pg_sleep, system catalog,
     data-modifying CTE) and 4 normal example queries from `bench/questions.yaml`; they fill the
     SQL box and run.
   - A collapsible "Schema" panel from `GET /schema` (allowed tables/columns only).
   - Escape every value rendered from the API (no innerHTML with data). A strict
     `Content-Security-Policy` header for `/` (self only).
   - Keep the design quiet and technical: one accent color, system fonts plus a monospace, no
     gradients, no emoji labels.
2. **Tests**: `/` returns 200 HTML with the CSP header; static assets served; a test that the JS
   never uses `innerHTML` with API data (grep-style test is fine); existing API tests still pass.
3. **Demo GIF** `docs/demo.gif` (< 4 MB, ~15–25 s): `scripts/record_demo.py` starts nothing itself —
   it expects the app running on a given URL (document: `API_PORT=8010 docker compose up -d --build`
   or uvicorn against the test DB). It drives headless Chrome (installed at
   `/Applications/Google Chrome.app`) through: a normal query → a blocked denied-column query →
   the whole-row oracle being blocked → stacked DROP blocked → pg_sleep blocked; captures frames
   (screenshots) and assembles them with `ffmpeg` (installed at /opt/homebrew/bin/ffmpeg) into a GIF.
   Prefer Chrome's DevTools protocol via a small dependency (e.g. `playwright` as a **dev** dependency
   using the system Chrome channel) only if it installs without downloading browsers; otherwise
   use `--headless=new --screenshot` per state with URL hash parameters that the page reads to
   pre-fill and auto-run a query (add `#sql=...&run=1` support to the page for this). Also save
   2 static PNG screenshots (`docs/screenshot-query.png`, `docs/screenshot-blocked.png`).
   Use your own `--user-data-dir` in a temp folder; kill Chrome afterwards.
4. **Architecture diagram** `docs/architecture.svg`: question → model → validator → read-only
   role → read-only transaction → result, with what each layer blocks; readable in GitHub light and
   dark (explicit background, or two versions with `<picture>`).
5. **README rewrite** (keep the existing Setup / Benchmark content, reorganise around it):
   1. one-line pitch + the GIF;
   2. "Why": an LLM can write any SQL, so the model is treated as untrusted;
   3. the layers (diagram + a short table: layer → what it stops → where in code);
   4. Benchmark headline: rejected / neutralized / harmful, false blocks, and the per-layer table
      (from the M4a results block — keep the `bench:guardrails` markers intact), with one sentence on
      why both layers are needed (what each misses alone);
   5. Try it (docker compose, open `http://127.0.0.1:8010/`, `/query` and `/ask` curl examples);
   6. Live-model benchmark: how to run, "no published numbers yet";
   7. Limitations (honest: Postgres only; allowlist must be maintained; the model can still give a
      wrong-but-safe answer; DB-only layer allows harmless catalog reads; etc.);
   8. Development, project layout.
6. Docs: DECISIONS (static page without a build step; CSP; how the GIF is made), CHANGELOG.
